# 整体架构（TypeScript 版）

> 2026-10-04 起草，**待用户确认后再写代码**。
>
> 用户要求（2026-10-04）：
> - 技术选 TypeScript：网页画面，后端计算。
> - **先定好整体框架**：按作用分好层次和模块，预留接口，以后加功能、加模块不用动核心。
> - **NPC 有通用模板**。
> - **AI 能按职业群体控制 NPC，也能控制其中一部分；命令要特别简洁。**
>
> 这份文档管"怎么搭"；玩法见 [design.md](design.md)。

## 0. 旧项目的教训 → 这次的对策

| 旧项目的痛点 | 这次的对策 |
|---|---|
| 加一个功能要改十几个文件（桥接层、观测、命令表、存档、网页、测试……） | **模块化**：一个功能 = 一个文件夹。模块向核心**登记**自己的命令、简报段落、存档、配置、画面图层；核心文件不用改 |
| 命令表、帮助文字、提示词要手工保持一致 | 命令只**定义一次**（参数格式 + 说明 + 例子），解析器、AI 的命令说明、界面按钮、文档、测试全部从定义自动生成 |
| AI 要做微操 | NPC 自己按行为干活；AI 只给**群体**下**长期命令** |
| 规则散在角色、桥接层、界面里 | **所有对世界的改动只走"动作"接口**：NPC、AI、上帝、测试调用的是同一套规则 |
| 迷雾、存档、配置是后来硬塞进去的 | 第一天就预留：每个势力有**情报库**、每个模块自带**存档段**和**配置段** |
| 性能是事后才发现的问题 | 数据按紧凑数组存、固定节拍、远处粗算；**压测是测试的一部分，超时就算失败** |

## 1. 分层

```
┌────────────────────────────────────────────────────────────┐
│ client   浏览器：画面图层、界面面板、镜头、输入 → 命令              │
└───────────────▲──────────────────────────────────────────────┘
                │ protocol（WebSocket 消息格式，前后端共用）
┌───────────────┴──────────────────────────────────────────────┐
│ server   宿主：主循环、WebSocket 网关、视野订阅、存档文件、管理接口  │
├────────────────────────────────────────────────────────────┤
│ ai       AI 席位：唤醒、简报拼装、模型调用、回复解析 → 命令          │
├────────────────────────────────────────────────────────────┤
│ game     玩法模块：world / economy / jobs / military / …（每个一个文件夹）│
├────────────────────────────────────────────────────────────┤
│ engine   通用内核：实体与组件、调度、事件、命令总线、模块注册、      │
│          空间索引、寻路、存档框架、远近模拟切换（不知道"木头"是什么）│
├────────────────────────────────────────────────────────────┤
│ shared   基础：类型、可重现随机数、数学、ID                       │
└────────────────────────────────────────────────────────────┘
content    纯数据：职业、物品、建筑、地形（JSON/TS 数据，无逻辑）
```

**依赖只能向下**：`shared ← engine ← game ← ai ← server`。
`client` 只依赖 `protocol` 和 `shared`，绝不碰模拟代码。
模块之间只能通过对方 `index.ts` 导出的**公开接口**访问，并且要在 `requires` 里声明。
这些规则由 `tests/arch.test.ts` 检查（解析每个文件的 import），**违反就是测试失败**，不靠自觉。

**工具**：
- TypeScript strict 模式；
- Vite 打包前端，PixiJS v8 画图，`ws` 做 WebSocket；
- Vitest 跑测试，tsx 运行后端；
- zod 做参数、配置、协议的格式校验；
- TypeScript 严格模式（含未使用变量检查）+ 自写分层测试（`tests/arch.test.ts`），不额外装 ESLint，省空间。

## 2. 核心契约：模块（GameModule）

**以后加任何功能，都是写一个模块并登记它。** 模块能向核心提供的东西全部列在这里，没有的就不用填：

```ts
export interface GameModule {
  id: string;                        // 'jobs'
  requires?: string[];               // ['world', 'economy']
  components?: ComponentDef[];       // 新的组件（数据列）
  systems?: SystemDef[];             // 每节拍要跑的逻辑
  actions?: ActionDef[];             // 改世界的规则（唯一入口）
  orders?: OrderDef[];               // 群体可接受的长期命令类型
  behaviors?: BehaviorDef[];         // NPC 能做的行为
  commands?: CommandDef[];           // AI/上帝/界面可用的命令
  events?: EventDef[];               // 本模块会发出的事件
  briefing?: BriefingSection[];      // 往 AI 简报里贡献的段落
  wake?: WakeRule[];                 // 哪些事件会叫醒 AI
  views?: ViewChannel[];             // 往前端推送的数据
  content?: ContentSchema[];         // 本模块认识的数据类型（如"职业"）
  config?: ConfigSchema;             // 可调参数（带默认值和校验）
  save?: SaveHandler;                // 存档段 + 版本迁移
  install?(api: ModuleApi): void;    // 兜底：订阅事件、查别的模块公开接口
}
```

启动时注册表会做四件事：
1. 按 `requires` 排序；
2. 检查 ID 和命令名有没有重复；
3. 把各模块的系统按阶段排好；
4. 把命令汇总成解析器和 AI 的命令说明。

**任何一项不合规，启动直接报错**，不会悄悄带着问题运行。

前端有对应的 `ClientModule`：`{ id, layers, panels }`。一个模块如果有画面，就在前端写同名的图层，接收后端同名 `ViewChannel` 推来的数据。

### 2.1 一个节拍里发生什么（固定每秒 10 次）

```
1. 收命令     本节拍之前到达的命令按到达顺序校验、执行（AI、上帝、界面、测试都一样）
2. 系统阶段   input → ai_npc（NPC 选行为）→ act（执行动作）→ move → resolve（战斗/产出）
              → economy → population → post（统计、史册）
              每个系统声明自己的阶段和频率（如每 10 拍一次、每游戏日一次）
3. 事件派发   本节拍产生的事件发给订阅者（史册、AI 唤醒、前端通知、其他模块）
4. 推送       给每个已连接的网页按视野推送变化
```

**模拟是可重现的**：随机数只用带种子的 `shared/rng`，模拟代码里禁用 `Math.random` 和 `Date.now`（ESLint 规则拦住）。
同一个种子加同样的命令记录，结果逐字节相同。这样 bug 可以复现、整局可以复盘、可以不开画面快进。

## 3. NPC 通用模板

### 3.1 实体与组件

每个 NPC 是一个**实体 ID**，数据按"列"存放：同一种数据的所有 NPC 放在一个紧凑数组里。
**所有 NPC 都有基础组件**：

| 组件 | 字段 | 说明 |
|---|---|---|
| `Identity` | 名字、势力、所属城镇 | |
| `Transform` | x, y（米）、所在地区 | |
| `Motion` | 速度、路径、目标点 | |
| `Vitals` | 血量、上限 | |
| `Carry` | 物品种类、数量、上限 | 村民规格：只拿一种东西 |
| `Profession` | 职业 ID、熟练度 | |
| `Brain` | 当前行为、行为状态、所属命令 | 见 §3.3 |
| `Membership` | 所在编组、是否锁定 | 见 §4 |
| `Lod` | 细算 / 粗算 | 见 §6 |

**可选组件**按需挂：`Combat`（攻防、射程）、`Equipment`（兵器等级）、`Notable`（名人：性格、忠诚、野心）……
以后的模块可以随时加新组件，比如"信仰"，不用改 NPC 本体。

### 3.2 职业 = 数据

**加一个职业，通常只是加一份数据**：

```ts
// content/professions/woodcutter.ts
export default defineProfession({
  id: 'woodcutter', name: '伐木工', short: '木',
  tags: ['worker', 'gatherer'],          // 选择器能用标签选人：@worker
  stats: { speed: 1.0, carry: 10, hp: 100, attack: 2 },
  defaultOrder: { type: 'work', resource: 'wood' },
  behaviors: ['gather', 'deliver', 'flee', 'idle'],   // 能做的行为，按优先级
  tools: { axe: { rate: 1.5 } },          // 国库里有斧头时效率加成
  upkeep: { food: 1 },                    // 每天口粮
  train: { from: 'any', cost: { food: 5 }, days: 1 },  // 转职成本
});
```

只有出现**全新种类的活**时，才需要写新行为（比如"捕鱼"），而且行为写在对应模块里。

### 3.3 命令 → 行为 → 动作（三层，各管一件事）

```
AI 命令     "派 @木:5 伐木 北林"
   ↓ 生成/修改一条
长期命令    Order { type:'work', resource:'wood', area:'北林' }   ← 一个编组共用一条
   ↓ NPC 每次空闲时，按命令和职业挑行为
行为        gather → deliver → gather → …（状态机，脚本驱动）
   ↓ 每一步调用
动作        actions.moveTo / gather / deposit / attack / build   ← 规则唯一入口
```

- **Order（长期命令）由模块定义**：`work`、`guard`、`move`、`attack`、`escort`、`idle`……
  每种命令声明哪些行为能完成它。
- **Behavior（行为）接口**：

```ts
export interface BehaviorDef {
  id: string;
  fits(npc, order, ctx): number;        // 0 = 做不了；越大越优先
  start(npc, ctx): void;
  tick(npc, ctx): Status;               // 'running' | 'done' | 'failed'
  coarse?(npc, ctx, dt): Status;        // 远处粗算版本；不写就用通用的"按时间推进"
}
```

- **Action（动作）是改世界的唯一入口**：
  - 校验规则（够不够得着、背包满没满）；
  - 修改数据；
  - 发出事件；
  - 返回 `{ ok, reason }`。

  NPC 行为、AI 命令、上帝干预、测试调用的是同一批动作，规则只写一份。

**很省**：500 个伐木工共用一条 Order。改命令只改那一条，NPC 下次空闲时自然换活，不用逐个通知。

## 4. 指挥：选择器 + 简洁命令

### 4.1 选择器（选中哪些 NPC）

| 写法 | 意思 |
|---|---|
| `@木` / `@伐木工` | 我所有的伐木工（职业简称或全称） |
| `@木@青石城` | 青石城的伐木工 |
| `@木:5` | 5 个伐木工（优先挑空闲的、离得近的） |
| `@农:30%` | 三成农夫 |
| `@worker` | 按标签选：所有干活的 |
| `#一队` | 已编好的队伍 |
| `阿三` | 指定某个人 |
| `@木,@石` | 多选：伐木工和石匠 |
| `*@河口镇` | 河口镇所有人 |

选择器只能选到**自己势力**的 NPC，由命令总线统一校验，命令本身不用操心。

### 4.2 两种指挥方式并存

1. **定比例（最省事）**：`比例 青石城 农50 木20 石10 兵20`
   - 系统会自动把空闲的人分配或转职到这个比例。
   - 平时 AI 只要调比例就行。
2. **直接派（要精确的时候）**：`派 @木:5 伐木 北林`
   - 被直接派出去的人会**锁定**，自动比例不再调动他们。
   - 用 `放 @木@北林` 解除锁定，还给自动分配。

### 4.3 命令示例（第一批，草案）

```
比例 青石城 农50 木20 石10 兵20      职业比例
派 @木:5 伐木 北林                   派工
转 @农:10 兵                         转职
编 @兵@青石城:20 一队                 编队
攻 #一队 赤焰.落霞镇                  进攻
守 #二队 青石城                       驻守
撤 #一队                             撤退
建 兵营 青石城                        建造
税 青石城 15                          税率
信 赤焰 北林归你，河口归我，如何？      私信
告 赤焰背约在先，天下共讨之            公开宣告
约 赤焰 互不侵犯 30天                  提议条约
想 赤焰兵多粮少，拖到冬天再打           心里话（只有上帝看得到）
```

AI 一次回复可以写多行，每行一条命令。执行结果会逐条出现在下一份简报开头。

### 4.4 命令定义一次，到处生效

```ts
export const assign: CommandDef = {
  id: 'assign', verb: '派', aliases: ['assign'],
  who: ['lord', 'god'],
  args: [sel('人'), enumOf('活', workKinds), place('地点')],
  help: '把一批人派去干某种活（会锁定，直到"放"）',
  examples: ['派 @木:5 伐木 北林'],
  run(ctx, { 人, 活, 地点 }) { return ctx.orders.set(人, { type: 'work', resource: 活, area: 地点 }); },
};
```

这一份定义会自动用于：
- 文本解析器；
- AI 提示词里的命令表（按条件展开，命令多了也不会冗长）；
- 上帝面板的按钮和表单；
- `docs/commands.md`；
- **契约测试**：每条命令的每个例子都会在测试世界里真正执行一遍，必须成功。

命令总线：`来源（AI / 上帝 / 界面 / 测试 / 脚本）→ 解析 → 校验（权限、归属、迷雾）→ 下一节拍执行 → 结果 + 事件`。
所有来源走同一条路，所以**整局的命令记录就是复盘文件**。

## 5. 事件与情报（迷雾从第一天就有）

- **事件**有类型、有发生地点、有**可见范围**：
  - 谁看得到：所在势力、附近有眼线的势力、全体（公开宣告）。
  - 例子：`npc.died`、`building.done`、`settlement.besieged`、`treaty.broken`。
- **情报库（Intel）**：每个势力一份，记录"我知道什么、什么时候知道的"。
  比如"赤焰在北林约 60–80 人（3 天前，斥候报）"。
- **AI 简报只读情报库，不读真实数据**。所以信息不对称、撒谎、虚张声势天然成立。上帝和测试可以读真实数据。

## 6. 大地图与远近模拟

- **地图**：
  - 地区层：约 300–500 个地区，相互连成一张图；
  - 格子层：每格 2 米，按 64×64 格切成区块，按需生成，只存改动。
  - 生成函数只依赖地图种子，前端也可以自己算出地形。
- **空间索引**：网格桶。查附近的资源或单位，只查周围几个格子。
- **寻路**：
  - 远途在地区图上找路线；
  - 区块内用格子寻路；
  - 回仓库这类常用目的地用流场；
  - 每个节拍有寻路计算预算，超出的排队等下一拍。
- **远近切换（LOD）**：
  - 镜头附近、正在打仗、被上帝盯着的地区逐个细算；
  - 其余地区粗算，调用行为的 `coarse` 版本：走路按路程算到达时间，干活按速率算产量。
  - 同一个 NPC 的数据在两种模式间切换时连续，不会瞬移或丢东西。

## 7. AI 层

```
WakeRule（各模块贡献）→ 席位被叫醒
  → Briefing：各模块贡献段落（带优先级和长度预算）+ 上次命令的结果 + 心里话
  → Provider：OpenAI 兼容接口 / 脚本 AI（测试和压测用）/ 回放
  → Parser：逐行解析 → 命令总线
  → 日志：简报、原始回复、命令、结果、心里话（JSONL，给剧情面板和复盘用）
```

- **模型调用是异步的，不会卡住模拟**；可以限制同时调用的数量。
- 提示词放在数据文件里，命令表是自动生成后插进去的。
- **提示词只给事实和数字，不下指令**（沿用旧项目的原则）。

## 8. 后端与前端

- **后端**：
  - 主循环、存档（模块各存各的段 + 版本迁移）；
  - 管理接口：改配置、存读档、调时间倍率；
  - WebSocket 网关。
- **视野订阅**：网页把自己的镜头范围和缩放级别告诉后端，后端只推这个范围内的东西：
  - 近景：单位位置、状态（紧凑二进制格式）；
  - 中景：区块汇总；
  - 远景：地区层（领地、城镇、部队图标）。
- **协议消息**：`hello`、`subscribe`、`snapshot`、`delta`、`event`、`command`、`result`、`inspect`、`defs`。
  消息格式定义在 `protocol/` 里，前后端共用同一份类型，改了一边、另一边编译就会报错。
- **前端**：
  - PixiJS 画面图层（地形、资源、建筑、单位、领地、特效），每个图层对应一个模块；
  - HTML 面板：上帝面板、诸侯简报、心里话对照、史册、关系图；
  - 两次快照之间自己补帧。

## 9. 以后怎么加东西（照着做就行）

| 要加的 | 要做的 |
|---|---|
| 一个职业 | `content/professions/` 加一份数据。完 |
| 一种建筑 / 物品 | `content/` 加数据；有特殊效果的话，在相关模块加一个系统 |
| 一条命令 | 在相关模块的 `commands` 里加一个 `CommandDef`（带例子）。解析、AI 命令表、按钮、文档、测试自动跟上 |
| 一种活 / 行为 | 在相关模块加一个 `BehaviorDef`，在职业数据里写上它的 ID |
| AI 简报里多看一样东西 | 在模块里加一个 `BriefingSection` |
| 一个全新玩法（比如"宗教"） | 新建 `src/game/modules/religion/`：组件 → 系统 → 动作 → 命令 → 事件 → 简报 → 存档 → 配置 → 画面图层 → 测试；最后在 `game/index.ts` 加一行。**核心文件一个都不用改** |

新模块的模板用脚本生成：`npm run new:module religion`。

### 第 0 阶段落地时对模块契约的补充

模块安装是按 `requires` 排好的顺序**一个个**进行的，所以安装时还看不到排在后面的模块。凡是要用到"别的模块登记的东西"的，都走延后机制：

| 接口 | 什么时候生效 | 用来做什么 |
|---|---|---|
| `api.addBehavior(def)` | 立刻登记；职业行为表在全部模块装完后才定型（`brains.finalize()`） | 军事模块把"站岗 / 巡逻"加进士兵的行为表，不用改职业模块 |
| `api.addCommand(def)` | 全部模块装完、行为表定型之后才登记 | 命令要检查"它生成的长期命令类型存在、有人能接"，所以必须晚于所有模块 |
| `api.onStart(fn)` | 世界生成完、开第一拍之前 | 给开局的人分配职业和平时的长期命令 |

注册表的完整顺序：排序 → 逐个安装（组件 / 事件 / 长期命令 / 行为 / 参数类型 / 动作 / 系统 / 视图 → `install(api)`）→ 行为表定型 → 静态命令 → 延后命令 → 一致性检查（命令的长期命令存在、行为用到的动作存在）→ `onStart`。
